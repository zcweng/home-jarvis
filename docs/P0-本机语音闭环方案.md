# P0 本机语音闭环方案（MacBook Pro M4 24G）

> 变更：**暂不上 ESP32、先不用 MacMini**。在本机用「有线耳机当麦克风 + 电脑喇叭当输出」跑通完整语音控制回路，
> 跑通后再原样移植到 MacMini。硬件停摆从关键路径上拿掉——先证明"这东西值不值得做"，再谈"长耳朵"。
> 撰写日期：2026-10-23

---

## 0. 这个改法为什么是对的

前面两版方案的重心其实在手硬件（AEC、双麦、刷机）。但那个顺序有问题：**硬件只决定最后 10% 的体验（打断、远场），却要吃掉 80% 的时间和不确定性。** 换成有线耳机麦克风后，反而白捡三个好处：

| 好处 | 原理 |
|---|---|
| 近场拾音，识别率直接拉满 | 耳机麦距嘴 3~10cm，SNR 比 5 米远场高 20dB 以上 |
| 回声耦合大幅变小 | 耳机麦与笔记本喇叭的距离/指向决定了喇叭声泄漏很弱 → 打断的门槛从"必须 AEC"降到"双讲检测够用" |
| 全链路可观测 | 每个环节都在本机，能单独测、单独换、单独打日志 |

代价也要说清楚：**耳机塞耳朵里就听不到喇叭了**。所以实际用法是——耳机**只当麦克风用**，挂在领口/放桌上，输出仍走笔记本喇叭（macOS 允许输入输出分离，见 §2）。或者直接改用 AirPods 的麦克风做输入 + 喇叭做输出。

## 1. 目标架构（本机版）

```
        ┌── 有线耳机麦克风（3.5mm TRRS / USB-C） 16k mono ──┐
        │                                                   ▼
        │                              ┌────────────────────────────────┐
        │                              │  jarvis 状态机（Python 单进程）  │
        │                              │  IDLE → LISTEN → THINK → SPEAK  │
        │                              │        ↖______ FOLLOW_UP ______╱│
        │                              └──┬────┬──────┬────────┬─────────┘
        │                                 │    │      │        │
        │                    ┌────────────┘    │      │        └────────────┐
        │                    ▼                 ▼      ▼                     ▼
        │              silero-vad        sherpa-onnx  DeepSeek        edge-tts / piper
        │              (断句/双讲)        SenseVoice   (FC + 流式)     / macOS say
        │                                     │            │                │
        │                                     └─ 上下文/别名表 ─┴──────┐      │
        │                                                             ▼      ▼
        └──────────────────────────────────────────────► 工具层 → HA REST ─► [Docker: HA :8123]
                                                                              └ 小米官方米家集成(OAuth)
```

**一个进程、四个可替换的适配器（ASR / TTS / LLM / 工具）**，是本方案唯一的设计约束。理由：迁移到 MacMini 时只换配置，不换架构；将来接 ESP32 时，把"麦克风+喇叭"换成网络音频端点即可，状态机和工具层一行不动。

## 2. macOS 上必须处理的三个现实问题

### 2.1 插上耳机，输出会被偷偷切走

macOS 检测到 3.5mm 设备会**同时**把输出切到耳机、输入切到耳机麦。而你要的是"耳机当麦、喇叭当外放"：

> 系统设置 → 声音 → **输出** 选「MacBook Pro 扬声器」，**输入** 选「外置麦克风」

程序里不要写死设备索引（插拔一次就变），写**名字子串匹配**：

```python
in_dev  = pick(sd.query_devices(), "外置麦克风", kind="input")   # 无耳机时回落 "MacBook Pro麦克风"
out_dev = pick(sd.query_devices(), "MacBook Pro扬声器", kind="output")
```

另一个坑：**TRRS 接法有 CTIA / OMTP 两种**，老耳机是 OMTP，插上去麦克风不出声。如果"外置麦克风"电平一直是 0，先换一副耳机，别怀疑代码。

### 2.2 麦克风权限（TCC）

终端/IDE 第一次录音会弹「允许访问麦克风」。**必须用 GUI 终端手动跑一次**才能授权；用 `launchd` 直接拉起无头进程会**静默拿不到音频**（表现为一直静音，不报错）。所以顺序永远是：终端跑通 → 再写 launchd。

### 2.3 采样率不一致

耳机麦通常是 48kHz，ASR/VAD 要 16kHz 单声道。用 `soxr` 重采样（质量高、纯 C 实现），别用 `scipy.signal.resample`（慢且相位差）。

## 3. 组件选型（每项都给"为什么"和"坑"）

| 环节 | 首选 | 为什么 | 备选 / 坑 |
|---|---|---|---|
| 录音 | `sounddevice`（PortAudio） | macOS 原生支持、按名选设备方便 | `pyaudio` 编译常挂；`AVAudioEngine` 要 PyObjC，工程量大 |
| VAD | `silero-vad`（ONNX） | 断句准、抗噪、CPU 占用低 | `webrtcvad` 太粗糙，中文口语会切碎 |
| ASR | **sherpa-onnx + SenseVoice-small（int8）** | 中文/粤语强、带标点、**不依赖 torch**、M4 上 3 秒语音约 200~400ms | FunASR 精度略高但要拖 torch；whisper.cpp 静音段会幻觉 |
| LLM | DeepSeek（`deepseek-flash` 控制类 / `v4-pro` 闲聊） | 你已有 key；官方支持 function calling + 流式 | 别把思考模型放进控制链路 |
| TTS（快） | **macOS `say`（zh_CN 语音）** | 零依赖、离线、**<150ms 出声**，用来先跑通回路 | 机器感强，只适合过渡 |
| TTS（好） | `edge-tts` | 音质明显好、免费 | 需网络，首包 300~600ms |
| TTS（全离线） | `piper`（zh_CN-huayan-medium） | 本地、首包 100~250ms、可移植到 MacMini | 音色平；模型文件约 60MB 要单独下 |
| 播放 | `sounddevice` + 可中断队列 | 打断=清队列+停流，比 `afplay` 子进程干净 | 用子进程播放会残留僵尸声 |
| 家电控制 | Home Assistant（Docker）+ 官方米家集成 | 一次接入、全屋可管、状态能回读 | 下面 §5 有 macOS 专属坑 |

**TTS 建议路线**：`say`（Day 1 跑通）→ `piper`（Day 2 换音色，同时验证离线链路）→ 后期待定 CosyVoice2/IndexTTS。

## 4. 「怎么唤醒」：别一上来就啃唤醒词

唤醒词是中文语音助手里最容易浪费时间的一块（openWakeWord 以英文为主，中文要自己训）。用一个递进路线，每级都能独立产生价值：

| 阶段 | 方案 | 实现量 | 什么时候用 |
|---|---|---|---|
| **P0-a** | **PTT（按键说话）**：按住右 Option 说话，松开出结果 | 20 行 | Day 1，验证整条链路 |
| **P1-a** | `sherpa-onnx` KWS 中文关键词（"小智"） | 半天 | 想脱手时 |
| **P1-b** | 常开 VAD + ASR 首句**名称门控**（必须含"小智/管家"） | 半天 | 最省事的中文"唤醒词"，代价是常开 ASR（M4 上 CPU 可接受） |

**我的建议：先把 PTT 做扎实。** 桌面场景下，按键说话的成功率、抗误触发、可调试性全面碾压唤醒词，而且它天然解决了"打断"——按住键就是打断。等交互稳定了再花半天上 KWS。

## 5. Home Assistant 在 macOS 上怎么跑

```yaml
# docker/docker-compose.yml
services:
  homeassistant:
    image: ghcr.io/home-assistant/home-assistant:stable
    container_name: homeassistant
    restart: unless-stopped
    ports: ["8123:8123"]        # 不要用 host 网络：Docker Desktop for Mac 的 host 网络不可靠
    volumes: ["./config:/config"]
    environment: [TZ=Asia/Shanghai]
```

步骤：
1. `docker compose up -d` → 浏览器开 `http://localhost:8123`
2. 装米家集成（要求 HA Core ≥ 2024.4.4）：`cd config && git clone https://github.com/XiaoMi/ha_xiaomi_home.git && cd ha_xiaomi_home && ./install.sh /config`
3. 重启 HA → 设置 → 设备与服务 → 添加集成 → Xiaomi Home → OAuth 登录（**地区选对**，选错看不到设备）
4. 生成**长期访问令牌**（左下角个人资料 → 安全 → 长期访问令牌），写进 `.env` 的 `HA_TOKEN`
5. **先手动点灯验证成功**，再接语音

macOS 特有的两个坑：
- **mDNS 发现不了设备**：没关系，米家集成走云端 OAuth，不需要局域网发现
- 容器网络隔离下 HA 访问不到 Mac 上的服务需要用 `host.docker.internal`，反过来（Python 调 HA）用 `127.0.0.1:8123` 正常

## 6. 延迟预算（本机，估算；跑完用 §7 的脚本实测校准）

| 环节 | PTT + `say` | PTT + `piper` | 关键影响因素 |
|---|---|---|---|
| 切句（松手→判定说完） | 100~300ms | 100~300ms | VAD 静音阈值 |
| ASR（SenseVoice int8） | 200~400ms | 200~400ms | 语句长度、CPU 线程数 |
| LLM 首字 | 300~600ms | 300~600ms | `deepseek-flash` + 短 system prompt |
| TTS 首包 | 50~150ms | 100~250ms | `say` 进程启动 / piper 推理 |
| **首字合计** | **≈0.7~1.5s** | **≈0.7~1.6s** | edge-tts 会再加 300~500ms |

对照：小爱音箱一代（云端一问一答）约 2~3s 且不能连续；理想车机 <1s 是**端侧模型 + 端侧 TTS + 车载总线**换来的，本机这套做到 1.0~1.5s 已经很接近"不像智障"的分界线。

## 9. 迁移到 MacMini：把"搬家"提前设计好

从第一天就按可迁移方式组织，搬家才不会变成重写：

| 约定 | 做法 |
|---|---|
| 依赖 | `uv` + `pyproject.toml`（`uv sync` 一把装齐，不用碰系统 Python） |
| 配置 | 全部走 `.env` + `config/*.yaml`，**代码里零硬编码**；设备名、模型路径、HA 地址都从配置读 |
| 模型文件 | `models/` 目录，`.gitignore` 掉，用 `scripts/fetch_models.sh` 在目标机重新下 |
| 容器 | 只有 HA 一个容器，`docker compose up -d` 即可 |
| 常驻 | MacBook 上手动跑；MacMini 上写 `launchd/com.suke3.jarvis.plist`（开机自启、崩溃重启） |
| 音频设备 | 按名字子串匹配，两个机型的默认设备名不同也不需要改代码 |

**搬家 = 五条命令**：`git clone` → `uv sync` → `scripts/fetch_models.sh` → `cp .env.example .env`（改 HA 地址）→ `docker compose up -d && uv run jarvis`。

将来的升级路径（不返工）：
1. 想脱手 → 加中文 KWS 唤醒词（§4）
2. 想远场 → 加 ESP32-S3 端点，只替换 `audio/` 这一层，`app.py` 与工具层不动
3. 想全离线 → ASR 换 FunASR 本地、TTS 换 piper/CosyVoice2，LLM 换本地 Qwen3

## 11. 风险与边界（提前说清楚，别事后返工）

1. **半双工是 P0 的默认状态**：播报时不做打断，或只做"按键打断"。真·语音打断要等双讲检测/软件 AEC（BlackHole 虚拟声卡 + webrtc AEC），那是 P2 的事，也是将来上 ESP32 会自然解决的部分
2. **窗口必须从"播报结束"开始计时**：否则 LLM 1.5s + 播报 2~3s 会把 8 秒吃掉一大半，用户想接着说话时窗口已经关了（`WakeGate.hold()/release()`）
3. **`say` 的音色会劝退家人**：自用验证可以，给家人用之前一定要换 piper 或云端 TTS
4. **常开 ASR 的隐私与功耗**：P0 用 PTT 就是为了规避这条；上常开要加物理开关
5. **米家集成许可**：仅限"非商业性 Home Assistant 使用"，自家用没问题，做成产品不行（详见总方案 §8）
6. **`say` 的新版音色是空音频**：Eddy / Flo / Reed / Sandy 等「个人语音」类音色在 `say` 下只渲染 16ms 静音，且直接说话也只持续 0.5s（无报错），表现为"程序跑了但没声音"。必须用经典音色 Tingting / Meijia / Sinji
7. **`say` 冷启动约 750ms 且与文本长度无关**：开销全在进程启动，所以"首句先出声"要用 `direct` 模式（边合成边说，~50ms 起播）；需要指定输出设备时才用 `wav` 模式（渲染完再播）。长回复应按句切分、边渲染边播
8. **模型会编造"已执行"**：实测用户说"把客厅灯关掉"，模型回"客厅灯已经关了"但一次工具都没调，设备状态没变。prompt 单独堵不住，必须在编排层兜底（`chat_with_guard`：命令类话语未调工具 → 锁定 `tool_choice` 强制重问）
9. **TTS 反喂 ASR 有同音字陷阱**："再暗一点"会被识别成"再按一点"（àn 同音），测出来的 CER 漂亮不代表真人语音都稳
10. **HA token 明文**：`.env` 与 `docker/config/.storage` 里都是明文，MacBook 务必开 FileVault，别把仓库推到公开远端
