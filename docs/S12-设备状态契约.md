# S12 设备状态契约（/tmp 文件 · UDP · 音量语义）

> 2026-11-04 随 `tools/s12audio` + `tools/s12led` 修复一起定稿。
> 这份文档的存在原因：审查发现 4 个进程、3 个 Mac 端模块、2 个 shell 脚本
> 都在自由读写同一批 `/tmp` 文件，且**没有任何一处写明谁该写**。

---

## 1. 唯一写者原则

**每个共享状态只有一个写者。** 读者可以任意多，但不得回写。

| 文件 | 唯一写者 | 读者 | 语义 |
| --- | --- | --- | --- |
| `/tmp/jarvis-vol.pct` | **s12audio**（playback 线程） | `volumed`、`led-set.sh`（只读） | 当前实际生效的音量 0–100 |
| `/tmp/jarvis-mic.mute` | **volumed** | `led-set.sh`、`s12audio`（镜像） | `1`=麦克风已禁用 |
| `/tmp/jarvis-mac.ip` | **Mac 侧 `app.py`**（SSH 写入） | `volumed` | 回传 UDP 的目标 IP |
| `/tmp/jarvis-led-breath.pid` | **led-set.sh** 子 shell | `led-set.sh` | 呼吸动画 pid |

> 旧版 `ledd.sh`（FIFO 守护）已删除，灯环只剩一条实现：`led-set.sh`。
> `deploy.sh` 仍会清理设备上可能残留的 `jarvis-ledd` 进程与 `/tmp/jarvis-led.fifo`，
> 那是迁移动作，不是契约的一部分。

实现集中在 `tools/common/state_file.h`：只有 `jarvis_read_int` / `jarvis_write_int`。
写入是 **tmp + rename** 的原子操作，读者不会看到半截内容。

### 为什么 led-set.sh 不再写 pct

旧版本 `paint_volume()` 结尾有 `echo "$pct" > /tmp/jarvis-vol.pct`。
而 `s12audio` 又轮询这个文件当音量来源。结果是：

```
volumed 改音量 → led-set.sh 写 pct → s12audio 读到 → 可能再落盘 → ...
```

形成自激环，表现是「滑环时音量自己往上跑一格」。现在 pct 文件只由
`s12audio` 在**确认采纳**某个音量后写入，环被打断。

## 2. 音量语义（唯一曲线）

```
pct  ∈ [5, 100]        全链路唯一的音量真值（整数）
byte = 60 + round(20·log10(pct/100))      → 夹到 [0, 60]
gain = pct / 100  =  10^((byte-60)/20)
```

- **C 侧**：`tools/common/gain.h`（`jarvis_pct_gain` / `jarvis_pct_to_byte` / `jarvis_byte_to_pct`）
- **Python 侧**：`jarvis/volume.py::percent_to_gain_byte`（**逐点一致，有单测交叉验证**）
- **下限 5%**：低于此值直接夹到 5，不做「静音」——静音是 `mute`，不是音量 0。

> 曾有 3.9dB 那次误判的教训：**不要在不同地方各自实现一次曲线**。
> `tools/common/test_common.c` 里有往返一致性断言，任何一侧改动都会被抓到。

### 增益只施加一次

| 环节 | 是否施加用户音量 |
| --- | --- |
| Mac TTS `peak_db` 归一化 | ❌ 不是用户音量，是**响度归一化**，两者正交 |
| 下行 `F_VOLUME` 字节 | 只是**声明**音量，不是增益动作 |
| **设备端 `downlink_session` 收到 PCM 时** | ✅ **唯一施加点**（`pcm[i] * g_vol`） |
| 设备端 `F_VOLUME` 分支 | ❌ 只更新 `g_vol_pct`，不再二次乘 |

旧实现里 `g_vol` 有两个来源（pct 文件 + F_VOLUME 字节）且曲线不同，
「实际音量是多少」取决于哪条路径最后写——不可推理。现在所有入路都收敛到
`vol_set_pct()` 一个函数。

## 3. UDP 回传协议（设备 → Mac:8769）

`volumed` 用 ASCII 单行包，Mac 侧 `jarvis/volume.py::_udp_loop` 解析：

| 消息 | 含义 | Mac 侧动作 |
| --- | --- | --- |
| `V<pct>\n` | 用户转了音量环 | `set_percent(pct, led=False)`（灯已由设备画，避免 SSH 重复刷灯） |
| `M0\n` / `M1\n` | 麦克风启用 / 禁用 | `set_muted(bool)`，清会话态 |

包是**无连接 UDP**，丢包可接受：音量真值仍以设备为准，下一帧 `F_VOLUME` 会重新同步。

## 4. 状态文件格式

单行十进制整数 + `\n`。读取时非法内容一律回退到调用方给的默认值，
**不抛错、不阻塞**（设备侧没有好的错误处理去处）。

```c
int pct = jarvis_read_int(JARVIS_VOL_PCT_FILE, 70);   // 不存在 → 70
jarvis_write_int(JARVIS_VOL_PCT_FILE, pct);           // 原子写
```

## 5. 启动顺序依赖

```
1. Mac app.py  → 写 /tmp/jarvis-mac.ip
2. volumed     → 读 mac.ip / mute / pct，独占 event0
3. s12audio    → 打开 hw:0,0（必须先 /etc/init.d/pns stop）
```

`s12audio` 在收到第一条 `F_VOLUME` 之前，会用 pct 文件作为初始音量；
一旦收到过 `F_VOLUME`，就以 Mac 为准，不再回读文件。这样既照顾了冷启动，
又不会形成「设备写→设备读」的环。
