# 本地 TTS 太生硬 · 选型与实测

> 问题：`jarvis` 默认用 macOS `say` 念回答，听起来"一个字一个字拼出来"，不像人说话。
> 本文记录原因、已做的改善、以及四条可选路线（都在这台 M4 上实测过）。

---

## 1. 为什么 `say` 生硬

macOS `say`（经典音色 Tingting/Meijia）是**共振峰拼接式**合成：把预先录好的音节/半音节片段
按规则拼起来，再用规则做韵律。它的问题不是"音质差"，而是：

- 音节之间是**拼**的，没有连贯的协同发音（coarticulation）
- 韵律是规则生成的，句内起伏、重音、语气都很平
- 默认语速偏快（175wpm），长句一口气念完，没有自然停顿

Tingting 是 2007 年前后的技术水平，跟现在的神经 TTS 不是一代东西。

---

## 2. 已经做的两项低成本改善（免费、立即生效）

```bash
# .env
TTS_BACKEND=say
SAY_RATE=170            # 原默认 175 偏快；降到 170 明显松弛
```

代码里给句末自动插停顿（`jarvis/tts.py::_prosody`）：

```
"好的，客厅灯开了。还要调暗吗？"
→ "好的，客厅灯开了。[[slnc 200]]还要调暗吗？[[slnc 200]]"
```

`[[slnc N]]` 是 `say` 内嵌的静音指令，实测有效：同一句话加两处 400/300ms 停顿后
时长从 **4.41s → 5.14s**。

**效果**：节奏变自然了，音色还是老的。属于"止疼药"，不是"治病"。

## 3. 四条路线实测对比（MacBook Pro M4，2026-10-24）

| 方案 | 首包/合成延迟 | 采样率 | 自然度 | 网络 | 成本 |
|---|---|---|---|---|---|
| macOS `say`（改造后） | **482~789ms** | 24kHz | ⭐⭐ 拼出来的 | 无 | 0 |
| 本地 VITS · aishell3 | **96~187ms** | 8kHz ⚠️ 发闷 | ⭐⭐⭐ 韵律自然 | 无 | 0 |
| **本地 VITS · fanchen-C**（当前默认） | 496ms / 13字 · 1019ms / 25字 | 16kHz | ⭐⭐⭐⭐ | 无 | 0 |

### 语速（`TTS_SPEED`）

fanchen-C 原始语速偏慢（约 **3.6 字/秒**），日常中文是 **5~6 字/秒**，所以默认调到 **1.35**：

| 语速 | 25 字句子时长 | 字/秒 |
|---|---|---|
| 1.0 | 6.88s | 3.6 |
| 1.15 | 6.44s | 3.9 |
| **1.35（默认）** | 5.38s | **4.7** |
| 1.5 | 4.92s | 5.1 |

太高（>1.6）会开始有"赶"的感觉，字与字之间粘连。想试听：

```bash
.venv/bin/python -m jarvis.tts_neural "随便一句话" --speed 1.5
```
| edge-tts（微软晓晓） | **1695ms 首包 / 2366ms 全长** ❌ | 24kHz | ⭐⭐⭐⭐⭐ | 需出境 | 0（非官方接口） |
| 火山 / 阿里云流式 TTS | ~200~400ms（官方标称） | 24kHz | ⭐⭐⭐⭐⭐ | 国内 | 按量计费 |

### 关键结论

1. **`say` 的音色天花板就在这里**，调参只能修节奏，修不了音色。
2. **8kHz 的神经模型不可取**：韵律确实自然了，但频谱只到 4kHz，听起来像老电话，比 `say` 更难受。
3. **edge-tts 音质最好但延迟在国内不可接受**：实测首包 1695ms（到微软服务器的往返），
   对语音助手来说等于"说完话愣两秒"，体验比生硬更糟。只适合做兜底。
4. **真正合适的组合是"国内云 TTS（流式）+ 本地兜底"**：自然度最高、延迟最低，
   代价是每个字几分钱、以及要开通账号。

## 4. 怎么切换

### 4.1 本地神经 TTS（离线、免费）

```bash
./scripts/fetch_models.sh tts          # 下模型（中文 VITS）

# .env
TTS_BACKEND=neural
TTS_MODEL_DIR=models/vits-zh-hf-fanchen-C    # 22kHz，推荐
# TTS_MODEL_DIR=models/vits-icefall-zh-aishell3   # 8kHz，快但发闷
TTS_SPEED=1.0
```

模型缺文件时会自动回落到 `say` 并打印提示，不会让程序崩。

### 4.2 云 TTS（音质最好、延迟最低，要账号）

接入方式与 `TTS_BACKEND` 同构：新增一个 backend 类，把流式音频喂给 `Speaker`。
需要你提供：服务商（火山/阿里/腾讯）、AppID/Token、选定发音人。

## 4.3 数字必须转成中文再喂给神经 TTS

fanchen-C 的词典只有汉字音素，**阿拉伯数字是 OOV，会被静默丢掉**（日志里只有一行 `Ignore OOV '10'`）：

```
"好，10秒后叫你。"  →  实际念成 "好，秒后叫你。"
```

所以 `jarvis/textnorm.py` 在合成前做归一化（`TTS_BACKEND=neural` 时自动生效）：

| 原文 | 念出来 |
|---|---|
| 好，10秒后叫你。 | 好，**十**秒后叫你。 |
| 把亮度调到30% | 把亮度调到**百分之三十** |
| 空调26度 | 空调**二十六**度 |
| 下午3点15分 | 下午**三点十五分** |
| 2026年10月24日 | **二零二六年十月二十四日**（年份逐位读） |
| 26℃ | 二十六**摄氏度** |
| 13800138000 | 逐位读（长数字串按编号念） |

macOS `say` 和云端 TTS 本来就会自己展开数字，所以这层只对本地神经 TTS 生效。

## 5. 踩过的坑

1. **sherpa-onnx 2.0.0 的 macOS wheel 没有 espeak 前端（实测）**：
   piper 系列模型（`vits-piper-zh_CN-huayan-medium`）缺 lexicon，加载后报
   `phoneme_codepoints is empty, no lexicon, and no frontend available`，
   `data_dir` 指到 `espeak-ng-data` 也没用。→ **只能用带 `lexicon.txt` 的模型**
   （aishell3 / fanchen-C / matcha 系列）。
2. **模型必须校验字节数**：从镜像下载 `zh_CN-huayan-medium.onnx` 得到过 60MB 的残缺文件，
   加载时只报 `Protobuf parsing failed`，很容易误判成"模型不兼容"。
3. **`say` 的个人语音类音色（Eddy/Flo/Reed…）只渲染 16ms 空音频**，见 README 已知坑。
4. **神经 TTS 静默吞数字**：`10` 被 `Ignore OOV` 丢掉，句子变成"秒后叫你"。已在合成前做中文数字归一化，并有回归脚本 `scripts/selftest_tts_text.py`。

## 6. 建议

- **现在**：`TTS_BACKEND=say` + `SAY_RATE=170` + 句末停顿（已默认启用），先解决"听着累"
- **想更好又不想花钱**：本地神经 TTS（已设为默认，`TTS_BACKEND=neural` + `models/vits-zh-hf-fanchen-C`）
  —— 16kHz、13 字约 496ms、句级流水（播第一句时合成第二句）
- **想接近真人**：接火山/阿里云流式 TTS —— 这是唯一能同时做到"自然 + 低延迟"的路
- 别指望 `say` 调参调出人味，也别为了自然度牺牲 1.7 秒首包
