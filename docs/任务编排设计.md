# 多任务编排：一句话 → 任务 DAG → 并发执行 → 顺序播报

> 目标场景：用户说一句「今天天气如何？打开客厅灯，关闭晾衣架」，
> 贾维斯拆成 3 个任务，并行/按依赖执行，**谁先有结果谁先念**，中途可以问「做到哪了」或「取消第二件」。

代码在 `jarvis/tasks/`：`model.py`（数据模型）· `plan.py`（拆解与校验）· `graph.py`（LangGraph 适配）
· `runner.py`（并发闸门 + 依赖执行）· `announce.py`（串行播报）· `service.py`（提交/查询/取消/收尾）。
回归在 `scripts/selftest_tasks.py`（离线 95 项；`--real` 加真模型 + 真设备 8 项）。

---

## 1. 需求 → 实现对照

| 需求 | 落在哪 | 关键约束 |
|---|---|---|
| 语义解析 → 任务拆分 | `plan.Planner.plan()` | 一次 LLM 出 JSON，本地严格校验 |
| 依赖 DAG 构建 | `sanitize_tasks()` + `topo_order()` | 编造工具/悬空依赖/成环/超量一律丢弃，图必须可编 |
| 并行 / 串行调度 | `graph.run_graph()`（LangGraph） | 无依赖并行，有 `depends_on` 才串行 |
| 异步执行、不阻塞对话 | `service.submit_specs()` 起后台线程 | 主对话立刻回一句「好，三件事，我分开做。」 |
| 结果按返回先后依次播报 | `announce.Announcer` | 单线程 FIFO，念之前等主对话说完 |
| 无需播报的可以不反馈 | `TaskSpec.needs_voice` | `false` 只做不念，但仍进总结 |
| 并发度阈值 + 排队 | `runner.ConcurrencyGate` | 信号量，`status=queued` 就是"在排队" |
| 语音查询 / 取消 | `Tools.tasks_tool` → `describe()/cancel()` | 序号、名字片段、「全部」都能认 |
| 失败不重试 | `_run_leaf()` 单次 `dispatch` | 如实播报；依赖它的任务 `skipped` |
| 大任务拆子任务（sub-agent） | `TaskSpec.kind="subplan"` → 嵌套 `TaskRun` | 默认最多 2 层，子任务不逐条念 |
| 主会话不留细节 | `runner.summarize()` + `on_summary` | 历史里只有一句；明细进 `data/tasks/*.jsonl` |
| 夜间不打扰 | `TASK_ANNOUNCE=false` | 照常执行、只记账不出声 |

## 2. 为什么用 LangGraph

自研一个线程池拓扑排序也不难，但 LangGraph 直接给了三件我们本来要手写的东西：

1. **动态 DAG**：每次按规划结果现编一张图（`add_node` / `add_edge` / `START` / `END`），
   依赖边就是执行顺序，汇合（fan-in）自动等齐。
2. **同步节点跑在线程池里**：本项目的工具层是同步 httpx（HA、天气、搜索），
   `def node(state)` 会被丢进 `ThreadPoolExecutor` 并发跑——实测 0.35s / 0.30s 两个分支总耗时 0.38s，
   串行要 0.67s。**不需要**为了编排把 HA/天气改成 async。
3. **产出自带顺序**：`stream_mode="updates"` 按节点**完成先后**吐出结果（实测 0.05s 的先出、0.35s 的后出），
   正好是「结果按返回顺序播报」需要的信息。

它在可选依赖里（`uv sync --extra tasks`），因为会带进 `langchain-core` 等 16 个包，
而本项目的默认安装刻意保持最小。没装时 `TaskService.enabled()` 返回 False，
`jarvis/app.py` 直接走原来的单轮对话，一行都不坏。

### 踩过的坑

- **节点抛异常会整张图中断**，其他分支的收尾全部丢失（状态永远停在「进行中」）。
  所以 `runner._node()` 自己 `try/except` 到顶，并在 `_finalize()` 里把没收尾的任务标成失败。
- **别拿图的 `max_concurrency` 当并发闸门**。它按「图内同时在跑的节点数」算，嵌套子图各算各的；
  父节点占着槽位等子图时容易把自己等死。闸门放在**叶子工具执行**上，父任务不占槽位。
- **同步节点的返回值必须可合并**：并行分支都往 `state["results"]` 写，得用 reducer
  （`Annotated[dict, merge]`），否则后完成的分支把先完成的结果覆盖掉。

## 3. 数据模型

```python
TaskSpec(id, title, tool, args, kind, goal, needs_voice, depends_on)   # 规划产物，不可变
TaskRecord(spec, status, result, note, started_at, finished_at, ...)  # 运行期状态
TaskRun(id, text, tasks, depth, parent, announce_leaf, summary, ...)  # 一次提交；子任务是嵌套 TaskRun
```

状态单向流动：`queued → running → done | failed | skipped | cancelled`。
**没有重试、没有回滚**——需求明确要求「失败的任务不需要重试，告知结果即可」。

成功/失败的判定是**文案判定**（`model.looks_failed()`，含「没找到/不在线/失败/未启用…」）：
工具契约本来就是「返回值就是要念出来的那句中文」，没有结构化 error 字段。
宁可多判成失败（代价是多跳过一件依赖任务），也不要对用户演「已打开」。

## 4. 拆解与校验

一次 LLM 调用（`temperature=0`，`max_tokens=700`）返回：

```json
{"tasks": [
  {"id": "t1", "title": "查今天天气", "tool": "weather", "args": {"city": "成都"}},
  {"id": "t2", "title": "开客厅灯", "tool": "control", "args": {"device": "客厅灯", "action": "on"}},
  {"id": "t3", "title": "查客厅灯状态", "tool": "query", "args": {"device": "客厅灯"}, "depends_on": ["t2"]}
]}
```

`t3` 的依赖是模型自己推出来的（「再查一下状态」只有在开灯之后才有意义）。

本地校验（`sanitize_tasks()`）——**丢坏条目，保留能跑的**：

| 坏输出 | 处理 |
|---|---|
| 编造工具名（`turn_on_light`） | 丢弃该条 |
| 依赖不存在 / 自己依赖自己 | 丢弃该边 |
| 两个任务互相依赖（成环） | 丢弃后加的那条边，图仍可执行 |
| 件数超过 `TASK_MAX_TASKS` | 截断 |
| `kind=subplan` 但没写 `goal` | 丢弃 |
| 整段不是 JSON | `PlanResult.error`，调用方回退单轮 |

拆完只剩 1 件 → `submit()` 返回「只拆出 1 件任务」，主流程**退回普通单轮**：
没有并发收益，多一次播报反而更吵。

### 多意图门控（省掉没必要的规划请求）

`intent.looks_like_multi_task()`：按标点切小句、逐句看像不像「一件事」，≥2 句才交给编排。
口语的命令动词比守卫用的 `_CONTROL` 更松（「把客厅灯关了吧」「开一下」「升上去」都算）。
「任务/进度/取消」这类**聊任务本身**的话被排除，那是 `tasks` 工具的活。
代价可控：多判一次只花一次规划请求（约 1.2s），漏判则退回单轮（模型仍可一轮里调多个工具）。

## 5. 调度：并发闸门与排队

```
LangGraph 图（依赖边）        ConcurrencyGate(容量 2)
 t1 天气  ────────────────►  [槽位1] 工具调用  ─┐
 t2 开灯  ────────────────►  [槽位2] 工具调用  ─┤→ 谁先回来谁进播报队列
 t3 查状态 ─(依赖 t2)──────►  等 t2 完成 ───────┘
 t4 关空调 ────────────────►  queued（等槽位）
```

- 叶子任务必须先拿到槽位才把状态改成 `running`；拿不到就保持 `queued`（语音查询里就是「排队中」）。
- 取消是在等槽位时也能立刻生效的（`acquire(timeout=0.2)` 轮询取消标志），不会「取消后还在等」。
- 子任务组（`kind=subplan`）**不占槽位**：它要起嵌套图，占着槽位等子图就是自等死锁。
- 槽位唤醒顺序不保证严格 FIFO（信号量语义），但不会饿死——对家里这几件任务够用。

实测（`selftest_tasks.py`）：5 件 × 0.3s、容量 2 → 峰值并发 2、`queued_ever=3`、总耗时 1.6s（≈3 批）。

## 6. 播报：单线程串行、按完成先后

```
任务线程 A ─┐
任务线程 B ─┼─► queue.Queue ─► 播报线程（唯一）─► tts.speak(阻塞)
任务线程 C ─┘
```

1. 节点跑完立刻 `push`，队列顺序 = **完成顺序**（不是规划顺序，也不是耗时顺序）。
2. 播报线程一次只取一条，念完再取下一条 → **绝不叠音**。
3. 念之前先等主对话的喇叭空下来（`is_idle`，最长 12s），否则「三件事的结果」会和当前这句回答撞车。
4. 播报前后通知主循环（`on_busy`），主循环**在播报期间丢弃麦克风输入**：
   否则喇叭自己念的话会被 VAD 当成用户说话（项目里踩过：播完自己接自己一句）。
5. 不需要播报的（`needs_voice=false`）只记账；失败默认也念（`TASK_ANNOUNCE_FAILURES`）。

工具返回值直接念，**不再过一次模型**：省 1.2~1.9s 往返，也避免模型二次创作说错「已打开」。

## 7. 查询与取消

模型看到的是 `tasks(action, target)`：

- `query` → `describe()`：`现在手上的任务：第1件慢任务进行中；第2件第二件排队中；第3件第三件排队中。同时最多做1件，另外两件在排队。`
- `cancel` → `cancel(target)`：`target` 可以是 `2` / `第2件` / 任务名片段 / `全部`。

取消语义是**协作式**的：排队中的直接不跑；已在跑的 HTTP 调用没法硬掐，标成 `cancelled`
后**丢弃结果、不播报**（写进日志）。已经结束的任务取消会被拒绝：「刚才的任务都已经结束了」。

`prompt.md` 第 12 条明确要求模型用工具查进度，不许凭记忆编任务状态（和「编造已执行」同一类幻觉）。

## 8. 子任务（sub-agent）

规划器判断一条任务「还太大」时给出 `kind="subplan"` + `goal`（自然语言目标），
执行器在节点里**再问一次规划模型**，拿到子任务列表，跑一个嵌套 `TaskRun`：

- 嵌套 run 的 `announce_leaf=False`：子任务不逐条念，父任务把结果拼成一句话汇总（≤180 字）。
- 默认最多 2 层（`TASK_MAX_DEPTH=2`）；到顶时如实说「这件事太大，一层拆不完」，不装成功。
- 子任务与父任务共用同一个并发闸门，所以嵌套也不会突破「同时最多 2 件」。
- 子任务失败 → 父任务 `failed`，播报里带上子任务的情况。

## 9. 上下文控制

主会话历史**只留一句**：

```
（任务完成 2/3）查今天天气✓ 开客厅灯✓ 关晾衣架✗
```

细节（每次工具调用、耗时、返回值、嵌套关系）写 `data/tasks/<run_id>.jsonl`，
一次任务一个文件，跑完不再进上下文。轨迹示例：

```json
{"ts": 1762..., "run": "r20261109-232501-ab12", "depth": 0, "event": "run_start", "text": "今天天气如何？..."}
{"ts": 1762..., "run": "...", "event": "start", "task": "t2", "title": "开客厅灯", "status": "running", "tool": "control"}
{"ts": 1762..., "run": "...", "event": "done", "task": "t2", "status": "done", "ms": 4546, "result": "已打开吸顶灯。"}
{"ts": 1762..., "run": "...", "event": "run_end", "counts": {"done": 3}, "elapsed": 4.9}
```

总结在**下一次开口**前才并进历史（`Jarvis._flush_task_summaries`），
这样压缩/记忆回调都还跑在主线程上，不在后台线程里动会话状态。

## 10. 配置

| 变量 | 默认 | 说明 |
|---|---|---|
| `TASK_ENABLED` | true | 关掉就完全回到单轮对话 |
| `TASK_MAX_CONCURRENCY` | 2 | 同时最多几个工具任务；超出排队 |
| `TASK_MAX_TASKS` | 8 | 一句话最多拆几件（防模型拆出 15 件） |
| `TASK_MAX_DEPTH` | 2 | 子任务嵌套层数；1=不拆子任务 |
| `TASK_ANNOUNCE` | true | false=照跑不出声（夜间/自检） |
| `TASK_ANNOUNCE_FAILURES` | true | 失败也念一句 |
| `TASK_IDLE_WAIT` | 12 | 等主对话说完再播，避免叠音 |
| `TASK_LOG_DIR` | data/tasks | 明细 jsonl 目录 |
| `TASK_PLAN_MODEL` | 空 | 空=复用 `LLM_MODEL` |
| `TASK_PLAN_TIMEOUT` | 8 | 规划那一次请求的超时 |

依赖：`uv sync --extra tasks`（`langgraph>=1.0,<2`）。

## 11. 验证证据

`./.venv/bin/python scripts/selftest_tasks.py`（离线，95 项全过）：

- 意图门控 6 项：三件事识别、单件事不误判、任务查询/取消不进编排
- 拆解校验 20 项：白名单、成环、悬空依赖、超量截断、非 JSON、subplan goal
- 引擎 5 项：并行（0.38s vs 串行 0.67s）、依赖顺序、完成顺序、结果合并
- 执行 5 项：3 件按完成顺序播报 `['已打开客厅灯。','已关闭晾衣架。','成都今天多云…']`、不叠音、`on_busy` 6 次
- 并发 5 项：峰值 2、排队 3 件、总耗时按批次、播报条数
- 失败/免播报 10 项：不重试（attempts=1）、依赖跳过（并报原因）、失败照念、`needs_voice=false` 不念但进总结
- 查询取消 18 项：排队中/进行中/并发上限文案、按序号取消（编号与查询一致）、执行中取消不播报、整组取消
- 子任务 7 项：2 次工具调用、只汇总一句、日志有 `group_start`、`max_depth=1` 如实失败
- 上下文 5 项：总结只回调一次、不含明细、jsonl 有 `run_start/start/done/run_end`
- 接线 9 项：单件事不进编排、多件事回确认、总结并历史、播报期间拦麦克风、只排空一次
- 降级 5 项：没装 langgraph 时 `enabled()=False`、提交给得出原因、`tasks` 工具仍注册

`--real`（真 DeepSeek + 真 Home Assistant，8 项全过）：

- 真模型拆「今天天气如何？把吸顶灯打开，再查一下吸顶灯的状态」→ 3 件，`t3 depends_on t2`，规划 1164ms
- 真链路：天气 617ms 与开灯 4546ms 并行 → 查状态 2ms（依赖串行）→ HA 里 `state=on` 实测 → 复位 off
- 总结一句、明细落盘

顺带修掉一个坑：**DeepSeek 默认开思考**，规划请求 700 个 token 全烧在 `reasoning_tokens` 上，
`finish_reason=length`、`content` 为空 → JSON 永远解析不出来（表现为"模型没给出合法 JSON"，耗时 6s）。
现在 `jarvis/llm.no_thinking_body()` 统一给规划/记忆这类"只要 JSON"的请求关掉思考，
`agent_runtime` 走 SDK 时用的是同一套判定。
