# 家庭版「理想同学」落地方案 v1

> 目标：把家里"一问一答"的小爱音箱，升级成**能连续对话、记得上下文、能控制全屋米家设备**的语音管家。
> 现有硬件：小爱智能音箱 / 常开 MacMini (M1 16G) / 蓝牙耳机 / ESP32 主板。
> 撰写日期：2026-10-23

---

## 0. 结论先行

**买一块 ESP32-S3（带 PSRAM、支持双麦回采），在 MacMini 上跑开源「小智」服务端，用 Home Assistant 官方米家集成做家电控制层。**

- ESP32-S3 = 耳朵和嘴（唤醒词、回声消除、VAD 都在板子上跑）
- MacMini = 大脑（ASR → 大模型 → TTS，全在局域网内，1~3 秒出第一句）
- 小爱音箱 = **不刷机**，继续当"被控设备 + 音乐播放器 + 全屋播报喇叭"
- 蓝牙耳机 = 次级终端（夜间/私密/调试耳返），不做主入口

成本：先 ¥0 纯软件验证 → 再 ¥130~400 配端点 → 可选 ¥250 加中枢网关换本地控制。
体验边界：**能做到**免唤醒续聊、可打断、记得"再暗一点"；**做不到**车机级 <1s 首字和 4 麦阵列车载 DSP 的噪声鲁棒性。

## 1. 「理想同学」哪些能力能搬回家

| 车机能力 | 家庭可复现 | 说明 |
|---|---|---|
| 唤醒词 + 免唤醒短指令 | ✅ | ESP-SR WakeNet 支持自定义唤醒词 |
| 多轮上下文（"再暗一点"） | ✅ | 服务端 session + 摘要记忆 |
| 播报中被打断 | ✅ 有前提 | 必须有 AEC 硬件回采，否则音箱自己把自己吵醒 |
| 唤醒后连续对话窗口 | ✅ | TTS 结束后保持 6~10s 收音 |
| 车控 → 家电控制 | ✅ | 米家集成 → HA → MCP 工具 |
| 首字 <1s | ❌ | 云 LLM + 云 ASR 的现实是 1.5~2.5s |
| 4~6 麦波束 + 车载 DSP | ⚠️ | 2 麦 ESP-SR 的水平，客厅够用，厨房油烟机边不行 |
| 全离线 | ⚠️ | MacMini 可跑 FunASR + CosyVoice2，质量/延迟打折 |

一句话：**能力可复现 80%，体感打七折**。别按车机标准验收，按"比小爱聪明一代"验收。

## 2. 硬件怎么分配

| 设备 | 角色 | 必须？ | 关键说明 |
|---|---|---|---|
| MacMini M1 16G | 大脑：Docker 跑小智服务端 + HA + FunASR + TTS | ✅ 必须 | 16G 够用；官方文档给的全模块 + FunASR 参考配置是 4 核 8G（[OFFICIAL]） |
| ESP32 主板 | 语音端点 | ⚠️ 看型号 | **关键约束见下** |
| 小爱音箱 | 被控设备 / 音乐 / 播报喇叭 | 可选 | 不刷机的唯一正确用法 |
| 蓝牙耳机 | 次级终端、调试耳返 | 可选 | 单麦 + 无回采，做不了远场主入口 |

### 关于 ESP32：这块板子可能直接决定成败

ESP-SR 文档明确：**AFE（AEC 回声消除 / NS 降噪 / VAD / 波束成形）只支持 ESP32-S3、ESP32-P4、ESP32-S31**（[OFFICIAL: esp-sr README](https://github.com/espressif/esp-sr)）。老款 ESP32（无 PSRAM、无 SIMD）只能跑 WakeNet10s 唤醒词（v2.6.0 起支持），**没有硬件级回声消除，就做不了"播报中被打断"和真正的全双工**。

所以：
- 你的板子若是 **ESP32-S3 且带 8MB PSRAM** → 直接可用，配 2 个 INMP441 麦克风 + MAX98357A 功放即可（总价约 ¥130）
- 若是 **ESP32-S3-BOX-3 / 立创实战派 S3 / M5Stack CoreS3** → 小智固件已官方适配（171 个编译变体），刷完就能用，约 ¥99~400
- 若是**老 ESP32 / ESP32-C3** → 只能做"按键说话 + 唤醒词"，做不了全双工，建议放弃做端点，改买 S3

### 采购优先级（如果只花一笔钱）

1. **ESP32-S3 端点**（¥130~400）：没有它，整套方案只是个"电脑上的语音助手"
2. **小米中枢网关**（¥250 左右）：装了之后米家集成可**本地化控制**，指令延迟从云端 200~800ms 降到局域网内；同时覆盖蓝牙 Mesh / ZigBee 子设备。**这是性价比最高的第二笔钱**
3. 不加也行：先用 MacMini + 一个自带 AEC 的 USB 全向麦音箱跑通软件闭环

## 3. 三条路线对照（为什么选 B）

| 维度 | A. 刷小爱固件接管 | **B. 小智卫星（推荐）** | C. HA Assist 原生 |
|---|---|---|---|
| 入口硬件 | 小爱音箱 Pro（LX06）/ Xiaomi 智能音箱 Pro（OH2P） | ESP32-S3 / P4 | ESP32、手机、浏览器 |
| 麦克风/回声 | 设备原生（刷机后能力待实测） | ESP-SR AFE：AEC/NS/VAD/波束 | openWakeWord + Wyoming，AEC 弱 |
| 中文 ASR/TTS | 服务端 | FunASR / 火山流式 / CosyVoice | faster-whisper + Piper（中文机械感强） |
| 多轮上下文 | 要自己写 | 内置 memory 模块 | 要自己写 |
| 家电控制 | 要自己接 | MCP + HA | HA 原生 intent |
| 维护状态 | ❌ [THIRD-PARTY] Open-XiaoAI 已停止维护（2026-04 归档），MiGPT 已归档 | ✅ 活跃（2026-10 仍有提交） | ✅ 官方活跃 |
| 许可 | 固件 MIT，但刷机风险自担 | MIT | Apache-2.0 |
| 主要风险 | 变砖、失保修、只支持两个型号、上游停维护 | 要买板子 | 中文体验差、全双工弱 |

**结论**：主线走 B；C 的 Home Assistant 仍然保留——它是家电控制层，不是语音层；A 直接放弃（除非你手上正好是 LX06/OH2P 且愿意折腾）。

补充说明 A 的死穴：小爱音箱未刷机时**没有对外开放麦克风流**，只有米家云端的 `MiNA` 接口可被"劫持"问答（MiGPT/xiaogpt 的思路），本质是替换它的答案，拿不到音频帧，因此**单轮、不能打断、长文本 TTS 会被截断**。这条路的天花板就是"能聊但不像人"。

│    ├ LLM：DeepSeek flash（控制类）/ v4-pro（闲聊类）+ Function Calling     │
│    ├ TTS：火山流式（快）/ CosyVoice2（本地、可克隆）/ EdgeTTS（省钱）      │

│                          ▼                                               │

关键点：
- **音频只在局域网内流动**（ESP32 ↔ MacMini），只有 LLM 请求出网；如果换本地 TTS + 本地 ASR，可以做到"断网也能开关灯"
- 让小爱负责它擅长的（音乐曲库、闹钟），管家负责对话和跨设备联动，别重复造轮子

## 5. 关键设计（决定"像不像人"的部分）

### 5.1 会话状态机：连续对话的核心

```
IDLE ──唤醒词──→ LISTENING ──VAD 断句──→ THINKING ──首字 TTS──→ SPEAKING
                    ▲                                              │
                    └────────── FOLLOW_UP（6~10s 收音窗口）←────────┘
                                     │
                              静音超时 / 说"结束"→ IDLE
```

三条规则：
1. **FOLLOW_UP 窗口内说话 = 续聊，不需要再说唤醒词。** 这是"理想同学感"的来源，窗口设 6~10s，可用"等一下再说"临时拉长
2. **窗口内静音超时 → 自动退出**，避免一直收音造成的隐私焦虑和误触发
3. **放音乐/电视时降级**：只保留唤醒词触发，关闭免唤醒续聊（否则会跟着电视唱）

### 5.2 打断（barge-in）

- **前提是硬件 AEC**：ESP-SR AFE 在 S3/P4/S31 上提供回声消除，2026-04-28 还发布了面向全双工的新 AEC 算法（[OFFICIAL: esp-sr](https://github.com/espressif/esp-sr)）
- 链路：设备端 AEC 后的残留语音 → VAD 判定"人在说话" → server 下发 `abort` → 设备 flush 播放队列 → 立即回 LISTENING
- **没有 AEC 的退路（半双工）**：把播报按句切分，句间留 150~250ms 空隙，检测到能量突增就停——能用，但误断率高，属于将就
- 打断后要**继承上下文**："别放了，刚才那个灯开到 50%" —— 打断不应清空 session

### 5.3 上下文与记忆：三层

| 层 | 存什么 | 存哪 |
|---|---|---|
| L0 会话上下文 | 最近 8~10 轮原文 + 本轮工具调用结果（结构化） | 内存 / Redis |
| L1 家庭档案 | 成员称呼、房间别名、设备昵称、"我习惯把卧室灯调到 30%"、常用场景 | SQLite / YAML |
| L2 长期记忆 | "上周说空调要修"、"孩子下周三有家长会" | mem_local_short 摘要，或直接复用你已有的 OpenViking |

两个工程细节，收益极大：
- **指代消解**：维护 `last_entity` / `last_action` / `last_value`，把"它 / 那个 / 再一点 / 关掉"翻译成显式参数再调工具；翻译不出来就反问一次，别猜
- **工具结果回写上下文**："客厅灯已调到 20%"必须进上下文，下一句"再暗点"才能落到 10%，而不是重新猜设备

### 5.4 家电控制：别让模型裸奔

直接给大模型几百个 `entity_id`，它一定会瞎编。正确做法是**别名层 + 少而稳的工具契约**：

```yaml
# aliases.yaml —— 中文口语 → 实体
客厅大灯:   {entity: light.ke_ting_deng,   room: 客厅, type: light}
电视      : {entity: media_player.tv,      room: 客厅, type: tv}
主卧空调:   {entity: climate.wo_shi_kong_tiao, room: 主卧, type: ac}
```

工具只暴露 5 个：

| 工具 | 作用 | 备注 |
|---|---|---|
| `control(room, device, action, value)` | 开关/调亮度/调温度/开合窗帘 | 主力 |
| `query(room, device)` | 查状态 | "空调现在多少度" |
| `scene(name)` | 执行场景 | 回家/离家/睡觉/观影 |
| `announce(text, room?)` | TTS 播报 | 也能投到小爱音箱 |
| `timer(minutes, label)` | 定时/提醒 | 本地任务队列 |

- 设备清单**按房间/别名裁剪到 40 条以内**直接塞 system prompt；超过 40 条再做向量检索 top-k
- **危险设备（燃气、门锁、大功率插座）二次确认 + 声纹权限**，孩子声纹禁止
- 执行失败要**说人话**："客厅灯离线了，是不是被墙上的开关关掉了？"
- 延迟：云控制 200~800ms（估算）；上了中枢网关走本地可压到 <100ms

### 5.5 多人：声纹

服务端支持 3D-Speaker 声纹识别，与 ASR 并行，把说话人身份透传给 LLM（[OFFICIAL: xiaozhi-esp32-server](https://github.com/xinnan-tech/xiaozhi-esp32-server)）。用途：
- 称呼（"爸，空调开到 26 了"）
- 权限（孩子不能开燃气、不能改门锁）
- 个性化默认值（每个人自己的灯亮度）

### 5.6 延迟预算（估算，需实测校准）

| 环节 | 目标 | 手段 |
|---|---|---|
| 唤醒词 | 200~400ms | 设备端常听，不占主线 |
| VAD 断句 | 300~600ms | 静音阈值 400~600ms 可调；语义断句更准 |
| ASR | 200~500ms | FunASR 本地整句；流式再降 |
| LLM 首字 | 300~800ms | DeepSeek flash；控制类走严格 JSON 快路径 |
| TTS 首包 | 200~500ms | 火山流式最快；CosyVoice2 本地；EdgeTTS 最便宜 |
| **合计** | **1.5~2.5s** | 官方称流式配置比早期版本快约 2.5s（[OFFICIAL]） |

压低体感延迟的四招：
1. **首句先出声**："好的"两个字先播，别等整段合成
2. **TTS 按句流式**，边合成边播
3. **工具与播报并行**：先说"正在开灯"，同时下发指令
4. **别把思考型模型放进控制链路**：闲聊用 v4-pro，控制用 flash + 结构化输出

## 6. 分阶段落地与验收标准

### P0 软件闭环（1~2 天，¥0）

- MacMini 装 Docker Desktop；部署 xiaozhi-esp32-server（官方 `Deployment_all.md` 全模块）+ Home Assistant（Docker，host 网络）+ 米家集成（HACS 或 `install.sh`，要求 HA Core ≥ 2024.4.4、HAOS ≥ 13.0 [OFFICIAL]）
- 没上硬件前，用服务端自带测试页当麦克风：`main/digital-human` 执行 `python start.py` 后访问 `http://127.0.0.1:8006/index.html`（[OFFICIAL]）
- **验收**：三类指令（开关灯 / 调亮度 / 查状态）各 5 次，成功率 ≥ 90%；"再暗一点"连续 3 轮指代正确

### P1 端点上线（3~7 天，¥130~400）

- 刷 ESP32-S3 固件（小智固件 + ESP-SR 自定义唤醒词，需走官方唤醒词定制流程）
- **验收**：5 米安静环境唤醒率 ≥ 90%，开着电视 ≥ 70%；播报中打断成功率 ≥ 80%；端到端首字中位数 ≤ 2.0s（连续 10 次实测，用服务端 `performance_tester.py` 分项测 ASR/LLM/TTS）

### P2 变得好用（2~4 周）

- 别名表、场景、定时提醒、声纹、第二个端点（卧室）、播报送小爱
- 可选：中枢网关本地化；记忆接 OpenViking
- **验收**：连续 7 天不重启；误唤醒 ≤ 2 次/天；"帮我把空调开到 26 顺便说明天天气"这类多意图指令 ≥ 85% 正确
- ⚠️ 米家集成**不支持蓝牙、红外、虚拟设备**（[OFFICIAL](https://github.com/XiaoMi/ha_xiaomi_home/blob/main/doc/README_zh.md)）——如果你家空调是红外遥控款，这块要单独解决（中枢网关 / 米家万能遥控器）

### P3 加分项

- 语音指挥 MacMini 上的 Agent（"把这周的日志总结一下"）→ 走 MCP 的 **user-only 工具**（设备端 `AddUserOnlyTool` 明确用于"特权/用户主动触发、禁止模型自主调用"的动作），加二次确认，这是你作为 Agent 开发者的天然优势

## 8. 风险与合规（有几条要提前想清楚）

1. **许可证边界（重要）**：`ha_xiaomi_home` 用的是小米自有许可，**仅授权"为非商业性目的使用 Home Assistant"**，明确禁止"用于开发应用程序（APP）、Web 服务以及其他形式的软件"；且不得用"小米/米家"名义宣传（[OFFICIAL: LICENSE.md](https://github.com/XiaoMi/ha_xiaomi_home/blob/main/LICENSE.md)）。→ 自己家里用没问题；**如果四象未来想把这套做成产品交付客户，这条路直接封死**，必须走米家开放平台企业接入。小智（MIT）和 HA（Apache-2.0）没有这个问题。
2. **刷机风险**：Open-XiaoAI 仅支持 LX06/OH2P，且已停止维护；变砖、失保修、账号风险需自担。所以本方案不刷机。
3. **隐私**：走云 ASR/TTS 时语音会上传；要全本地可换 FunASR + CosyVoice2。ESP32 端点建议加物理静音开关。
4. **安全**：米家集成会把小米账号的设备证书/token **明文写入 HA 配置文件**（[OFFICIAL]）→ MacMini 开 FileVault，配置文件单独加密备份；**不要把 HA 暴露到公网**，远程用 Tailscale。
5. **稳定性**：常开 Mac 要关自动休眠和自动更新（`caffeinate` / 能源设置），否则半夜静默升级会带走你的管家。

## 附录 B：动手前先跑这三个检查

```bash
# 1) 端点与大脑是否通（MacMini 上）
curl -s http://127.0.0.1:8003/xiaozhi/ota/ | head -c 0   # 服务端健康检查，端口以实际配置为准

# 2) 分项测速：ASR / LLM / TTS 各自的真实延迟
python3 main/xiaozhi-server/performance_tester.py

# 3) 家电链路：HA 里能否直接控制（先排除米家集成问题，再谈语音）
curl -s -H "Authorization: Bearer $HA_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"entity_id":"light.ke_ting_deng"}' \
     http://127.0.0.1:8123/api/services/light/turn_on
```
